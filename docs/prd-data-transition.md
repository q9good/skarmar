# PRD 新模型的数据转换与导入

此文描述仓库内已实现的维护流程，不表示生产转换或真实工作簿对账已经执行。新模型为 `SKARMA_MODEL=prd_v1`，业务 schema 7；当前通用配置的默认值仍是 legacy，新版开发使用 `tools/start-prd-local.sh` 和独立新库。不能仅改这个变量来升级旧库。普通启动始终拒绝未经确认的混合数据库。用户另要求发布试用后，新增显式空白新基线入口，见下节；它不转换旧业务。

2026-10-26用户明确新版本尚未正式使用，不以旧版兼容或旧数据迁移作为开发、验收前置。下面的旧库转换章节保留为已有历史维护工具说明，不是本轮待执行任务。外部工作簿导入继续按用户确认的原文／来源留存、人工确认实际结果、显式映射、预览、去重和事务写入原则完善；不从旧记录推断训练完成情况。

## 新版试用的空白基线

2026-10-26用户要求先发布新版看效果。显式配置 `SKARMA_MODEL=prd_v1` 与
`SKARMA_PRD_BASELINE=empty_preserve_legacy_v1`，在原存储内建立空白新版业务表，
保留全部原账号、会话和旧业务表，不把旧业务复制进新版。只接受已知完整旧schema 1–10
且有有效管理员的库；未知或部分库拒绝。初始化及标记在同一事务内，失败全部回滚。
重复启动不清空新版；持久标记允许后续普通新模型启动。旧版页面写入被拒绝。
该入口不复用旧库转换回执，不生成虚假的导入来源或实践记录；也不开放自动删表回滚。
详细配置保护、验证与实际发布状态见[本次发布记录](cloudflare-release-2026-10-26.md)。

## 旧库转换（L-2）

转换在**原 SQLite 文件／原 Durable Object 的同一事务内**增加新表。保留全部原表、原有账号／密码哈希／会话、Worker、`SkarmaSpace`、`SKARMA_DB`、space 和域名。不得新建空实例、重置管理员或用示例数据替代。源版本必须完整为旧库迁移 1–10；未知表、缺表或超过 1000 个业务对象会拒绝自动转换，需另行设计。

### 语义与对账

- 目标保留 ID、已知版本和已知历史；类型、层级、明确状态和下次复盘日期转入新结构。旧领域、原日期、原复盘文字等完整留存于来源，不自动变成测量或新复盘结论。
- 方法保留 ID、当前版本和明确目标关联。旧库没有保存的方法早期版本不补造。
- 机构课记保留日期、当时课程和老师名称；明确的目标／方法关联转入新结构。自由文字目标说明只作原文。目录停用状态在建立历史快照后恢复。
- **每条家庭记录必须逐条选择** `archive`（仅存档）、`planned`（待干预）、`completed`（已完成）。后者仅接受原本就是完成态的记录，必须明确 `actual_goal_ids`；实际表现优先使用确认人提供的 `observations`，否则保留原逐目标表现。缺表现或未选择实际目标会拒绝整批转换。旧“活动”不自动变成方法，实际方法明确标为未知。
- 原家庭／课记的已存目标快照保留其原名称、版本和字段；旧库没有保存的历史祖先不按当前层级倒填，因此不承诺重构未知的历史祖先覆盖次数。
- 经验和困难保留明确关联及可找到的正式来源；只存档的旧家庭记录不冒充新模型正式来源。旧知识原状态／结论／来源完整保留；保留旧“已验证”为观察好用（helpful）和原依据，有明确历史实践来源的待验证经验为已尝试（try），其余为想法（idea）；旧停用经验继续停用。转换不制造实践票数，也不要求既有有效实践退回未尝试。
- 新修订的操作人是转换管理员，标明转换基线；不把转换管理员说成原记录作者。旧原文和历史保留在来源表／原表中。
- 原始业务资料逐行存档，包含旧历史、删除标记、导入来源与目录变更。认证资料不进入业务存档或 Excel。操作缓存和过期预览不复制到业务档案，但旧表本身保留。

### 执行步骤

1. 对要发布的源代码完成本机双运行环境演练。确认生产原 Worker／DO／space／精确来源私有配置，**不要在此阶段改为新模型**。
2. 安排维护窗口，停止其他客户端业务写入。保留当前完整程序和私密部署配置；准备可恢复的原库备份，并在隔离库演练恢复。业务 Excel 是核对资料，**不能当作包含账号的数据库备份**。CF 的可用备份／恢复能力必须在实际账号确认，不能假设套餐包含 Time Travel。
3. 仍在旧模型下，用已有管理员发出 `upgrade_preview`；保存返回的 `source_digest`、数量和逐条家庭记录，逐项作决策。预览不写业务数据。
4. 发出 `upgrade_commit`，输入为 `{source_digest,note,sessions:[{id,disposition,actual_goal_ids,observations:{目标ID:表现}}]}`。缺少任何旧家庭记录的决策会拒绝。提交时重新核对全部旧表摘要；并发旧写入导致 409。任何失败回滚全部新表和新数据，原表不变。
5. 保存脱敏摘要及**私有完整回执**、`baseline`。在维护窗口中将**原实例**的模型变量改为 `prd_v1`；保留原绑定和来源。CF 每次请求会检查配置；转换后仍使用旧模型配置会拒绝业务请求，须按此步骤完成切换，不要因拒绝而重建资源。原生服务需重启。
6. 用原账号验证登录；按 ID 核对目标／方法／知识、课记数量和按老师的历史月节数、逐条确认的家庭记录、关联和来源。新模型不生成原先没有的测量／票数。导出 Excel 再核对来源、数量和完整原文。此次真实对账尚未执行。
7. 开放写入前决定接受或回滚。正式开放后，保留原表作为只读档案，不再运行旧模型写入。

所有 HTTP 维护命令：`POST /api/data-transfer`，JSON `{kind,value}`；必须已有管理员登录、合法精确 Origin、`X-Skarma-Request: 1`、`X-Skarma-Transfer: skarmar.transfer.v1`。这不是公开 SQL 接口。`upgrade_preview` 无 value，`upgrade_commit` 使用上述输入。请求丢响应时，切到新模型后可以原管理员、**原样输入**重试获取原回执，不能修改决策后重复转换。

原生离线维护可使用（占位路径须替换为私有路径，服务先停止）：

```bash
SKARMA_DATABASE=/private/original.sqlite target/debug/skarma-api backup /private/before-upgrade.sqlite
SKARMA_DATABASE=/private/original.sqlite target/debug/skarma-api data-transfer-stdin --offline --username EXISTING_ADMIN < /private/preview-command.json > /private/preview-result.json
SKARMA_DATABASE=/private/original.sqlite target/debug/skarma-api data-transfer-stdin --offline --username EXISTING_ADMIN < /private/confirmed-command.json > /private/upgrade-receipt.json
```

`preview-command.json` 为 `{"kind":"upgrade_preview"}`；确认文件必须人工填妥上述 `upgrade_commit`，不要将私有文件放进 Git。CLI 只读取指定已有用户的公开身份字段来验证管理员角色，不读取／输出密码哈希。操作系统层面的数据库访问权与现有 `admin-reset` 维护命令同级，不能替代远端登录认证。

### 回滚边界

`rollback` 输入 `{baseline,note}`。只允许转换基线仍一致、原旧表摘要也未改变时，在同一事务内移除**固定白名单**的新表；认证表和旧表保留。随后将原实例模型变量改回 `legacy` 并重启／恢复原代码。若回滚响应丢失，先完成模型配置核对并验证旧数据，不要盲目再次删除表。

摘要包含新模型全部业务表、修订和操作记录，故**任何新业务写入后均拒绝自动回滚**，即使后来把内容改回原样也拒绝。预览与认证会话不算业务写入，回滚仍保留账号变化。已有新业务时采取前向修复或人工合并，不能丢弃新表、整库覆盖回旧备份或强改摘要追求回滚成功。

原生 `restore-stdin --offline` 现按明确的 `SKARMA_MODEL` 检查恢复副本，兼容旧库和新库；未知／不匹配模型不会替换当前库，恢复后会话全部撤销。此命令同样要求停止服务和私有备份。

## 腾讯工作簿映射（L-3）

管理员在「我的账号 → 导入与来源核对」选择 `.xlsx` 或 UTF-8 `.csv`，上传解析后逐表选择用途。10MiB 文件、64MiB 解压、最多20张表／每批1000条记录，额外受单个存储对象1MB JSON约束；超限须分批。不能把应用导出的多表 Excel 当作数据库恢复文件。

每次选择**稳定的资料来源标识**；每张业务表选择原表内非空、唯一的**来源编号列**。建议在腾讯表保留专用编号，避免用会改名的标题作身份。列名可不同，显式选择列进行映射。未识别的表必须明确选择“仅存档”；未映射列和值完整保留。

| 用途 | 明确映射的字段 | 保守边界 |
| --- | --- | --- |
| 目标 | 编号、名称、期限；可选说明、标准、上级 | 期限选择长期／中期／短期，或原列 long／medium／short；不推算进度 |
| 方法 | 编号、名称、明确目标；可选说明、步骤 | 至少一个目标；不从方法说明提取关联 |
| 经验／困难 | 编号、内容、至少一个明确目标或方法；可选依据、阶段和状态 | 可明确映射提出／已使用／已验证与使用状态；未指定阶段才为 idea；依据原文不生成票数 |
| 瞬间观察 | 编号、实际日期、原文；可选目标 | 不算家庭干预次数 |
| 机构课记 | 编号、实际日期、课程、老师；可选内容、老师建议、困难、明确关联 | 同名目录仅复用活跃项；停用项须先显式恢复，不因导入自动恢复 |
| 家庭计划／总结 | 编号、日期、时段、状态 planned／completed；计划、主／副目标及计划方法 | 完成态另须明确实际目标、实际表现和方法确认 used／none／unknown；used 须选择实际方法；不从文字推断实际使用 |
| 仅存档 | 全部原始字段 | 不生成业务记录或计数；相同原文重复行也逐行保留 |

关联单元格使用 `工作表名:来源编号`，多项用分号或换行分隔，如 `目标:G01；目标:G02`。只认当前上传批次中明确映射的来源，非相似名称匹配；分批时关联对象与所引用原行一起上传，同来源重复行会跳过。上级目标按长→中→短、方法→记录→知识顺序写入；类型／层级／日期／方法确认等业务约束仍由共用核心校验，失败整批回滚，不产生半条关联。

原表没有明确完成状态、实际目标与表现的训练文字，建议导为瞬间观察或仅存档，之后人工整理。不能为了凑旧版训练数量自动标成完成。

“生成写入预览”保存映射和当前业务摘要，不写业务；“确认导入”再次校验摘要，在单个事务内追加。预览有效1小时。其他人修改后会409，保留映射重新预览。相同预览重试返回原回执，即使预览后来过期。相同来源／同编号／同原文／同映射重新上传会跳过；同编号内容或映射变化会409，须回业务页面显式修订，不覆盖已有数据，也不因重导复活已删除对象。如果复用的目标／方法已在应用内修订，重复原记录仍可跳过；新增历史记录若引用它则会409，避免用当前新定义冒充原历史定义。应先核对原记录，将新资料仅存档后在业务页面人工整理；不得用新来源标识绕过去重。

批次回执可分页查看原始来源。新 Excel 增加「导入来源」「导入批次」「旧模型转换」，保留全字段与来源关系；公式表达式原样存档且不执行；有缓存结果时用于字段值，缺缓存时保留公式文字供核对。表头公式须先改为纯文字。原始值作为文字写入，类似 `=SUM(...)` 的内容不作为公式执行。认证表、密钥、本机草稿、离线上传队列和临时导入预览均不导出。

## 本地验收入口与尚需实测

- `cargo test --workspace --locked --offline`：转换、权限、并发摘要、回滚、去重、历史与关联专项。
- `node tools/check-prd-upgrade-runtimes.mjs`：原生 SQLite 与真正的 Rust Wasm／Miniflare DO，原存储转换→重启→未写入回滚→再转换→新增观察后阻止回滚。
- `node tools/check-prd-maintenance.mjs`：本机离线维护、禁止误建空库、备份、错误模型恢复拒绝及新模型恢复后会话撤销。
- `npm run test:prd-runtimes`：两运行环境真实 XLSX 上传、映射、原文留存、关联、重复导入、导出及重启。
- `node tools/check-prd-web.mjs smoke_prd_import_web.py`：真实浏览器上传、下拉映射、丢响应重试、来源核对及 Excel。

以上只使用合成数据。实际生产副本的转换对账、真实腾讯工作簿重导对账，以及家庭 iPhone／Android 真机键盘、桌面入口和持续使用体验仍需各自实际执行，不能由本机绿色测试替代。
