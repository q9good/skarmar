# lens-feasibility 评估报告

## 总评

PRD 0.2 在原则层面质量很高：适用关系、计划选择、实际使用、有效性证据四件事分离，未记录≠0，示例≠值，追加式历史，幂等计数——这些底线贯穿 R03/R10/R13/R15，并与现有 `crates/core` 的事务、版本、快照、墓碑机制契合，实现基础好。主要问题是没有把"讲给家人的精简概念"和"系统必须持久化的东西"分层：§3 写的是"四个核心对象＋两类记录"，但闭环实际依赖至少 8 类没有建模的过程实体。其中两个 P0 会让 Check→Act→Plan 无法闭合：**对象状态与复盘决定没有统一定义**，**"下一步"没有承载对象，也没有出口**。其次，§7 批次有多处依赖倒置：R13 口径排在 R02 均衡提示之后；R03/R05 的"追加已有经验/困难"排在 R10/R11 事件模型之前；稳定老师 ID 排在 R04 重做之后。另外，"不考虑历史兼容"之后，§5/R14 中约三分之一的兼容条款可以删除，应借此改为新基线 schema 一次到位。

## Findings

### F-FN-1 对象状态与复盘"决定"没有统一定义，Act 步骤无法落地
- 严重度: P0
- 位置: §3.1（"当前状态""验证阶段"）、R02②④、R03、R06、R07 默认排序、R10 阶段、R11 优先级/解决/重开、R12 统一流程"作出决定"、R13"在途目标""停滞"；源码 `crates/core/src/model.rs`（`GoalStatus`、`GoalProgress` 7 值、`FollowUp.status: String`）、`crates/core/src/store.rs:874-892`（困难只允许 `pending/active/resolved`，经验只允许 `pending/verified/stopped`）、`apps/client/src/planning.ts`（`overdue` 标注为"已逾期（历史状态）"）
- 问题: PRD 各处引用了大量状态，但从未给出每类对象的状态集合、复盘可做的决定，以及决定对应的状态转换：
  - 目标：在途、维持、重点推进（R02），已内化（R01），暂停关注（R06 新增），达成与归档分开（R03），已完成（R07），停滞（R07/R13），待观察（R06）；
  - 方法：置顶/需注意、使用中、已停用/发现不适合、已归档（R07）；
  - 经验：想法/已有实践（§3.1），提出→可尝试→验证有帮助，暂停/停用（R10）；
  - 困难：未解决/已解决/重新开启、暂停、优先级、待核对（逾期）、停滞（D04"停滞困难每周"——自动判定还是用户确认？R11 只说"提示"）。
  
  现有 `GoalProgress` 把状态和历史标签混在一起，与 PRD 的集合对不上。三处的决定集合各不相同，也都没有映射到状态变化：R12 只说"作出决定"，R03 是"继续／调整／达成"，R11 是"继续／调整／请教老师／暂停"。
- 影响: 以下行为都无法实现成确定逻辑：R02 的"在途目标"过滤和"维持/重点推进"标识；R07 的五级默认排序；R12 的到期计算（暂停后还排期吗？）；R11 的升级规则（"连续两次无变化"需要结构化的变化判断字段）；R13 的"在途/停滞"统计。验收场景 6、7 也写不出期望值。
- 建议: 新增 §3.3「状态与复盘决定」，每类对象一张表。不考虑兼容，可直接替换 `GoalProgress`：
  - **中短期目标**：`未开始 / 重点推进 / 维持 / 暂停 / 已达成`，另有独立的 `已归档` 标记。**长期方向**：`关注中 / 维持 / 暂停`。
    - 可做的决定：继续（不变）；调整（必须写调整内容，生成新版本）；标记达成；转维持；暂停（必须写回看日期或"不排期"）；恢复；归档。
    - "停滞"不是状态，是复盘事件里的一个结构化判断值。
  - **困难**：`待处理 / 跟进中 / 已解决 / 暂停`，另设 `优先级: 普通/重点`（重点＝每周回看）。
    - 每次跟进事件必须选择 `变化判断: 有改善 / 无变化 / 更困难 / 无法判断`，R11 的"连续两次无变化／更困难"按此字段判定。
    - "待核对"是逾期时的派生展示，不是状态。
  - **经验**：`想法 / 可尝试 / 已验证有帮助（附条件）/ 暂停 / 停用`。
  - **方法**：`使用中 / 暂停 / 停用`；`需注意` 是独立布尔字段，并要求写明原因。
  - **统一规则**：
    - 每个决定都写入复盘事件（见 F-FN-3）。
    - 状态只能通过决定改变，或通过编辑表单改变并留下修订说明。
    - 暂停的对象不进入 R12 到期队列，也不参与 R02 的少覆盖排序。

### F-FN-2 "下一步行动"没有承载对象和出口，复盘结论回不到下一次计划
- 严重度: P0
- 位置: §1.1 核心价值、R01 今天顺序、R02④、R03"下一步"、R05"将老师建议加入下次计划""请父母查看"、R11 跟进字段、R12"下一步至少说明做什么，负责人…可直接转计划草稿"、§3.2"待整理列表"
- 问题: 产品核心价值是"每次观察能影响下一次行动，每次复盘能留下可追溯的决定"。但"下一步"在四处各自出现，从来没有被定义成一个可查询、可完成的对象：R03 的逐目标 next_step 文本，R11 的下一步＋负责人＋下次日期，R12 的下一步＋负责人＋可转计划草稿，R05 的老师建议→下次计划。具体缺口：
  1. **计划时看不到**：R02 第④步只展示"相关未解决困难与可用经验摘要"，不展示该目标尚未执行的下一步。复盘时写下的"下次在游戏里先示范两次"，除非当场"转计划草稿"，否则下次计划时不会出现。
  2. **今天页没有位置**：R01 的顺序里只有"到期及逾期复盘"，没有"待整理（请父母查看）"和"指派给我的下一步"。
  3. **"待整理"一词两用**：§3.2 指未绑定目标/方法的经验/困难素材，R05 指老人标记"请父母查看"的课堂材料。两者的状态和出口都不同，却同名。
  4. **只有到期队列，没有完成记录**：周末复盘做完后，家人无处查看"这周末我们决定了什么"。这和"不增加独立目录"并不矛盾，缺的只是一份只读的完成摘要。
- 影响: Check→Act 的产出停留在各对象详情里，Act→Plan 只剩"立即转草稿"一条路。老人请父母处理的材料、复盘时指派的事项都可能无人看到，闭环在最关键的一环断开。
- 建议:
  - **定义系统对象「下一步」**：放在 §3.1 的"两类记录"之外，家人不需要单独维护目录。字段：内容；关联目标/方法/困难/经验；来源（复盘事件/干预总结/课堂观察）；负责人（默认填写者）；建议日期；状态（待做/已纳入计划/已完成/取消）。R03 的逐目标"下一步"、R11、R12、R05 的"值得接着做的事"都生成此对象。
  - **R02④ 改为**："选中目标即显示：该目标待做的下一步、未解决困难、可用经验。下一步可一键纳入本次安排，纳入后状态变为'已纳入计划'，并记录计划 ID。"
  - **R01 补"给我的待办"区**：包括到期复盘、待整理课堂材料、指派给我的下一步，汇总一行显示数量，可展开查看。
  - **拆开"待整理"**：§3.2 的未整理素材改名为"未绑定"。"待整理"只用于 R05 的课堂材料队列，状态为：`待处理 → 已认领（谁）→ 已处理`，已处理时附结果（已转困难/已补经验/已纳入计划/无需处理）。
  - **R12 复盘队列**：增加"本周期已完成"折叠区，只读列出本次复盘做出的决定和生成的下一步。

### F-FN-3 核心对象之外的过程实体没有建模，§5 不足以指导实现
- 严重度: P1
- 位置: §3.1、§3.2 关系图、§5 数据补齐表、§7 批次 B；源码 `crates/core/migrations/001–010`、`crates/core/src/lib.rs` `Command`、`apps/client/src/workflow.ts` `mergeState`
- 问题: 闭环实际依赖下列持久化实体。它们散见于各 R 正文，§3 关系图和 §5 表格只覆盖了一部分，也没有关键字段和唯一性约束：
  - 复盘事件（R12）；
  - 复盘安排：每个对象的周期、到期日、暂停（R12）；
  - 下一步（见 F-FN-2）；
  - 经验使用反馈（R10，需 `unique(经验, 来源记录)`）；
  - 困难跟进尝试（R11）；
  - 待整理条目（R05）；
  - 家庭设置：固定复盘日、月度序次（R12）——当前完全没有家庭级设置存储，`AppState` 只有业务对象；
  - 方法版本（R07）——当前只有乐观锁 `version`，没有 `pathway_revisions`；
  - 经验派生关系（R10"派生原则保留原经验"）——§3.2 图中没有这条边；
  - 计划来源（R05"用于新计划"、R12"转计划草稿"）——session 需要记录来源；
  - 干预中的长期关注点（见 F-FN-4）。
- 影响: 按"四个对象"估算会严重低估批次 B。每个实体都要新增 `Command` 变体、核心 store 函数、导出工作表、客户端 `mergeState` 分支和测试，遗漏任何一项都要到验收时才暴露。
- 建议: §3 分两层表述：
  - 「家人理解的概念」：保持四对象＋两记录，不变。
  - 「系统自动保存的过程记录（家人不需维护目录）」：逐项列出名称、由哪个操作产生、关键字段、唯一性/幂等键、能否修改或作废。
  
  §5 按此重写为实体清单，不再写兼容条款（见 F-FN-16）。§3.2 关系图补四条边：经验→经验（派生）、复盘事件→下一步→计划、课堂观察→待整理条目、干预→长期方向（关注点）。

### F-FN-4 长期方向在干预/课记中没有承载位置，"长期关注点/长期观察"无法实现
- 严重度: P1
- 位置: R02⑤"可附带长期关注点"、R03"长期方向可有观察"、R13"长期观察"、R01 长期卡片；源码 `crates/core/src/model.rs` `Goal::is_trainable`（排除 `Level::Long`）、`crates/core/src/store.rs` `save_session` 完成校验（拒绝长期目标作为 target，且每个 target 必须有 outcome）
- 问题: 现有记录只允许中短期目标以主/副/复习角色参与，完成时每个 target 都要选处理结果。PRD 要求在一次干预中"附带"长期关注点、记录长期观察但不判定掌握，却没有定义它的数据形态：是新角色还是独立列表？要不要 outcome？R13 的"长期观察：独立标识本次明确关注点**或**展示下级关联证据"用了"或"，口径是二选一还是两者都算不明确。§5 也没有列出这一项。
- 影响: R01 长期卡片的"最新观察"、R13 的长期观察统计、§1.2 推荐的长期目标（分享关注、表达需要、参与共同活动），都只能通过下级中短期目标间接体现。长期方向恰好是承载"好奇、交流、韧性"的层级，却在记录层不可见。
- 建议: R02/R03 写明："干预和课记可附带 0–N 个长期关注点（角色 `关注`）。关注点只记可选观察文本，不要求处理结果，不计入中短期覆盖表。"R13 拆成两项分列显示、不相加：
  - `长期关注次数`：明确选为关注点的不同记录数；
  - `下级证据次数`：按当时层级快照统计的中短期命中数。

### F-FN-5 §7 批次存在依赖倒置，A 批过载
- 严重度: P1
- 位置: §7 批次表及"R14…随每批完成"段；R02②③、R03、R05、R07、R08、R13；源码 `apps/client/src/planning.ts` `buildPlanning`、`crates/core/migrations/008_lesson_options.sql`
- 问题:
  1. **统计口径晚于均衡提示**：R02②③（A 批）要展示覆盖次数、最近一次、实际方法/标签分布，口径却定义在 R13（C 批）。现有 `buildPlanning` 只有目标覆盖，实际方法和标签分布都是新口径。
  2. **R03/R05 依赖 B 批的事件模型**：R03/R05 的"更新已有困难/为已有经验补一次使用"在 A 批，依赖的 R10/R11 反馈与尝试事件在 B 批；R05 的"提炼为经验草稿"也依赖 B 批的经验阶段。
  3. **T10 方法快照（A 批）依赖方法版本历史（R07，B 批）**：没有 `pathway_revisions`，就无法"按当时版本回看"。
  4. **稳定老师/课程 ID（C 批）晚于 R04 课记重做（A 批）**：现有 `lesson_options` 以 `(kind, value)` 为主键。A 批按名称重做后，C 批还要再改一次表单和存储。
  5. **到期提醒依赖 R12（B 批）**：R02②"待复盘原因"和 R01"到期及逾期复盘"都依赖 R12 调度。A 批只能显示现有的目标提醒，PRD 没有说明这段过渡期的形态。
  6. **A 批内容过多**：A 批同时包含老人课记、计划/总结重排、T10、R15 全量文案、R16、跨页返回、待整理队列。老人流程和父母计划流程彼此独立，捆在一起会拖慢最高频、风险最低的老人课记上线。
- 影响: 按现有顺序实施会返工（R04 改两次、方法快照补做），或者在 A 批交付"看得见但没有数据"的提示。
- 建议: 用下面的顺序直接替换 §7 批次表：
  - **A0 基础**：新基线 schema（F-FN-16）、§3.3 状态集合（F-FN-1）、稳定老师/课程 ID＋名称快照、方法版本表、R15 文案目录与 Field 规范、R14 草稿/返回机制（F-FN-15）。
  - **A1 老人课记**：R04、R05、R16、待整理队列最小版（标记/认领/处理）。
  - **A2 计划与总结**：R02、R03、T10 实际方法＋快照、长期关注点（F-FN-4）、R13 中"目标覆盖／实际方法／活动标签"三项口径及金标准数据（F-FN-11）。若 B 尚未完成，R03 先只提供"新建困难/经验"，不提供"追加到已有"，并在 PRD 中写明。
  - **B 复盘与知识**：R10–R12、下一步对象（F-FN-2）、R06 结构化观察、R07 排序（依赖 F-FN-1 的状态和 F-FN-6 的期望频率）。
  - **C 回顾**：R08 明细/月切换/导出、R09 热力图与时间轴、R13 色阶与目标进展。
  
  同时删除 §7 中"历史兼容随每批完成"的表述。

### F-FN-6 "少覆盖方向靠前"与"均衡不要求次数相同／频次不表示进展"存在设计矛盾
- 严重度: P1
- 位置: R02②（"少覆盖方向靠前""均衡不要求次数相同""明确维持目标和正在重点推进目标"）、R07 默认排序第三级、R13"未覆盖与停滞"；源码 `apps/client/src/planning.ts`（`rows.sort((a, b) => a.count - b.count || …)`）
- 问题: 按绝对次数升序排序，隐含的基准是"各目标次数应当相近"，这与"均衡不要求次数相同"相冲突。维持类目标本来就低频，会长期占据顶部制造噪声；正在重点推进的目标次数多，反而沉底——而它恰好是父母准备安排的对象。PRD 提出要区分维持目标和重点推进目标，却没有让这一区分进入排序。R07 的"与近期少覆盖的在途目标相关"也继承了同一问题。
- 影响: 均衡提示会持续推荐错误的方向，家人很快学会忽略它；排序还可能被读成"次数少＝能力弱"，与 R13 的告诫冲突。
- 建议:
  - 给目标增加可选的"期望关注频率"（每周／每两周／每月／不设），或由状态推导默认值：重点推进＝每周，维持＝每月，暂停＝不参与排序。
  - R02② 改为按"距上次天数 ÷ 期望间隔"降序排列；未设期望的按距上次天数排列；表格同时显示"期望 vs 实际"。
  - 文案写明："排在前面表示比你们设定的节奏更久没练了，不表示能力落后。"
  - R07 第三级改为"与超出期望间隔的在途目标相关"。

### F-FN-7 方法与经验边界不清，家庭已有实践没有明确落点，"实际使用"与"有效性证据"分散两处
- 严重度: P1
- 位置: §1.3 表格、§3.1（方法"适用条件"、经验"适用边界"）、R07"不把经验正文复制进方法"、R10、R11"提炼为经验／方法调整"、D10
- 问题: 方法和经验都在描述"某个做法在什么条件下有帮助"，也都有条件字段。家庭已经在用、来自老师、观察有效的做法（D10、§1.3 的筷子辅助）该录为方法还是经验，PRD 没有说：
  - 录为方法：有使用次数，但没有有效性阶段；
  - 录为经验：有阶段，但 R03 只确认"实际方法"，经验的使用只能靠手动 +1。
  
  R11 的"方法调整"也没有对应操作：是改方法正文，还是生成新版本？
- 影响: 同一做法可能被分别录成方法和经验，实际使用计数（R07/R13）和有效性证据（R10）对不上，"四件事分离"原则在数据层被稀释。
- 建议:

### F-FN-18 实际方法确认与活动标签确认应采用不同规则

### F-FN-22 追加式事件的更正与作废规则未定义
- 严重度: P2
- 位置: R10"独立反馈需可修改纠错""多人可补不同观察"、R11"跟进历史不可被一个最新结论字段覆盖"、R12"改错字不算完成复盘"、§2"删除仍仅管理员可用"
- 问题: 反馈、跟进、复盘事件都是追加式的，但没有规定出错时怎么处理：
  - 成员误点 +1、记错结果时，只有管理员能删除——成员能否作废？
  - 同一来源有多人补观察且结果冲突时（一人记"有帮助"，另一人记"不明确"），计哪一个？

## 亮点（值得保留、不要在下一轮改坏的设计）

- **四件事分离**：§3.2"适用关系、计划选择、实际使用、有效性证据是四件不同的事"，以及场景 4"计划 A、实际 B"。这是整份 PRD 数据可信度的基石；F-FN-7/18 只是让它在方法与经验之间贯彻得更彻底。
- **空白与零的区分**：R13"未采集显示未记录""空白不能解释为没有陪伴""最近一次不受窗口限制""最近 30 次标明实际起止"；R06"未记录不补成失败"，不制造进度百分比。
- **R15 示例与值分离**：示例不进入草稿、请求、统计和 Excel，空白按真实空值校验。规则清楚，可以直接写成自动化测试。
- **R04 课记提交**：两个按钮，复用同一 ID；同日同老师同课允许重复，但给出提示；请求重试严格去重。现有 `lessons.rs` 已按内容相等实现幂等，可以直接沿用。
- **R08 只统计节数**：稳定身份＋当时名称快照，没填观察也计一节，金额线下算（D03）。范围收敛得当。
- **R10/R11 追加式证据**：+1 记录的是一次实际使用，不是点赞；同时收集"不明确／没帮助"；同一来源只计一次；没有自动升阶阈值。逾期只标"待核对"，不推断为没有进展；绝不因提醒变多就自动提高干预强度。
- **§3.2 直接关联与经方法关联分开展示**：标注关联来源，按 ID 去重；解除关联不删除记录，也不改变其他绑定。
- **R06 模板只改变引导文案**：目标标准与实际观察分开保存，不从示例或自由文本中提取虚假的基线。
- **复盘是操作而不是目录（D06）**：应保留。F-FN-2 只补只读的完成摘要和"下一步"出口，不新增需要家人维护的页面。
- **R16 只改显示名**：不重建资源，不做全仓字符串替换。
- **架构上的可行性红利**：原生 SQLite 与 Cloudflare DO 共用 `crates/core` 的同一份业务实现（`Sql` trait），新增实体只需实现一次。目标快照、修订表（`goal_revisions`/`session_revisions`）、删除墓碑（`deleted_records`）、操作幂等表（`operations`）都可以直接复用到新的事件表。
